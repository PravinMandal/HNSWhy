## 1. Project vision

The application will allow users to create their own knowledge bases by uploading documents such as PDFs, TXT and Markdown files.

The general workflow is:

1. User uploads a document.
2. We extract its content and perform chunking.
3. An embedding model generates embeddings for those chunks.
4. We store documents, chunks and embeddings in SQLite.
5. Embeddings are loaded into an in-memory VectorStore for efficient access.
6. Users can explore their knowledge base and ask questions through the frontend.

The central focus of this project is our **own vector search engine, implemented from scratch**.

## 2. Core vector search engine

We are implementing two approaches: BruteForce and HNSW.

**BruteForce:**

BruteForce searches every vector in VectorStore, calculates its distance from the query embedding and returns the nearest neighbours.

It provides exact nearest-neighbour results according to the selected distance metric. However, scanning every vector becomes expensive as the dataset grows. We will use it as our exact-search baseline and for correctness comparisons.

**HNSW:**

HNSW is the main engine we are building.

The graph should store vector references/IDs rather than duplicating actual embedding data. The embeddings remain in VectorStore in RAM.

During search, HNSW navigates its layered graph, retrieves the required vectors from VectorStore for distance calculations and performs approximate nearest-neighbour search.

Once we retrieve the relevant vector IDs, we use them to fetch the corresponding chunks from SQLite. These chunks and the user's question are passed to an LLM to generate the final answer.

The responsibilities are:

- SQLite: persistent storage and source of truth.
- VectorStore: actual embedding vectors in RAM.
- BruteForce: exact nearest-neighbour search.
- HNSW: graph connections, vector IDs and approximate search.

Do not simply import an existing HNSW implementation or vector database. The core HNSW algorithm must be implemented by us.

Focus on correctness, performance and proper testing, particularly with approximately 100k vectors on our available hardware.

Use the existing HNSW specifications and configuration as a starting point, including M=16, M0=32, efConstruction=200 and efSearch=50, unless there is a strong technical reason to change them.

Remember that exact nearest-neighbour search does not automatically guarantee semantic relevance. Evaluate HNSW recall against exact search, and evaluate the RAG output separately.

## 3. Embedding and LLM flexibility

Initially, we plan to use Ollama for local embedding generation and LLM inference.

However, the application must not be rigidly dependent on Ollama.

Our hardware may not have enough resources to run larger models, so we should also support external APIs.

- Embeddings should work with either a local model or an external embedding API.
- Answer generation should work with either a local LLM or an external LLM API.
- The embedding provider and LLM provider must be independently configurable.

Keep these integrations clean and modular so we can add or switch providers without rewriting the application.

Also handle embedding compatibility properly. Track the provider, model and dimensions used to generate embeddings. Don't mix incompatible embedding spaces in the same index. Provide a clear strategy for re-embedding when the embedding model changes.

## 4. Data consistency and system behaviour

Keep SQLite as the persistent source of truth. VectorStore and HNSW should be maintained in memory and reconstructed when the backend restarts.

Important requirements:

- Maintain stable document IDs and chunk IDs in SQLite.
- Maintain separate runtime vector slots and a reliable mapping between slots and chunk IDs.
- Support incremental insertion when new documents are uploaded. Never rebuild the entire index on every upload.
- Support deletion using tombstones or another correctly implemented approach without corrupting graph traversal.
- Rebuild VectorStore and HNSW from SQLite during backend startup.
- Handle failed operations without leaving SQLite and the in-memory index inconsistent.
- Consider thread safety and synchronization when uploads, deletions and searches happen concurrently.
