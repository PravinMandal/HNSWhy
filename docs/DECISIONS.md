# HNSWhy — Decisions

> One page of "why", so the project does not re-litigate the same choices every
> week. Status: **accepted** unless marked stretch/open. If another doc conflicts
> with this file, this file wins. Change the decision here first, then update the
> docs. Last updated: 2026-10-22.

---

## D1 — v1 is graded on SIFT-100k, not SIFT-1M

**Decision.** The headline run is the first 100,000 vectors of SIFT-1M, all 10,000
queries, with ground truth generated by our own brute force over that exact prefix.
SIFT-1M is an optional single-configuration scale run **after** v1 ships.

**Why.** 100k is 51.2 MB of vectors, builds in minutes, and can be iterated on in a
single session. 1M is 512 MB and makes every sweep and every brute-force
ground-truth pass 10× more expensive. The claim is about the algorithm and the
measurement, not about the largest possible N. A valid 100k answer key is worth more
than an invalid 1M one.

**Consequences.** Every chart, README line, resume bullet, and showcase page says
`N = 100,000` unless a measured 1M row exists. 1M is never a sweep. The architecture
supports 1M; the schedule does not depend on it.

**Revisit.** After S22, if the 100k run is stable and the 1M build fits the time
budget, run one 1M configuration and add a separate, clearly labelled row.

## D2 — Ground truth is generated for the exact dataset, never borrowed

**Decision.**

| Dataset | Base | Queries | Ground truth | Use |
|---|---:|---:|---|---|
| `siftsmall` | 10,000 | 100 | shipped `siftsmall_groundtruth.ivecs` | loader proof only |
| `sift10k` | first 10,000 of 1M | 1,000 or 10,000 | **our BF top-100, IDs + distances** | CI / integration |
| `sift100k` | first 100,000 of 1M | 10,000 | **our BF top-100, IDs + distances** | graded v1 |
| `sift1m` | 1,000,000 | 10,000 | shipped `sift_groundtruth.ivecs` + BF sample | optional scale run |

The shipped SIFT answer key is defined over **all 1,000,000 vectors**. It is invalid
on any subset. Never score a 100k or 10k index against it.

For `sift10k` and `sift100k`, generate the top-100 by brute force over that exact
base and query set. Store IDs **and distances**, checksum the file, and record the
generator commit/flags. Commit a **self-contained CI bundle** under
`tests/fixtures/sift10k/`: the first 10k base, a fixed 1k query set, GT IDs +
distances, query IDs, and sha256. For `sift100k`, commit only the GT + IDs + hashes;
the 100k base stays in gitignored `data/`. The generator is the same BF code that is
under test, so validate a 100-query sample against an independent float64 reference.

**Tie rule.** Recall is distance-threshold based: a returned item counts if its
distance is ≤ the true k-th distance + `1e-6`. Report ID-overlap recall separately.
SIFT squared-L2 is integer-valued, so exact equality is usually enough; the epsilon
is a safety margin.

## D3 — 10,000 queries for the headline; 1,000 only for smoke tests

**Decision.** Headline, README, showcase, resume, and the SLO point use all 10,000
SIFT queries. A fixed 1,000-query subset is allowed for per-PR smoke tests and
regression comparisons; it is labelled `PRELIMINARY` and never published as the
headline.

**Why.** At `p ≈ 0.90`, 1,000 queries gives a 95% interval half-width of about
±1.9 pp. A lower-bound gate at 0.90 needs an observed recall near 0.919, so a
genuinely good 0.92 index passes only about 56% of the time. At 10,000 queries the
half-width is about ±0.6 pp and the same gate is stable.

**Consequences.** The 1k smoke test may use a wider floor (e.g. 0.88) and must be
paired with a frozen baseline. CIs for mean recall use a query-level bootstrap;
Wilson is used only for genuinely binary metrics (exact R@1, perfect-top-10 rate).

## D4 — Layer 0 uses fixed-capacity flat adjacency, not CSR

**Decision.** Layer 0 stores `M0` neighbour slots per node in one flat
`std::vector<uint32_t>` (`N * M0`) plus a `std::vector<uint16_t>` degree array.
Pruning swap-erases within the node's fixed slots. Upper layers are sparse and may
use per-node small vectors (or per-layer slabs); the `vector<vector<...>>` ban applies
to layer 0 and to per-vector float storage, not to the thin upper layers.

**Why.** CSR is a static layout. HNSW is built incrementally: insert, back-edge
pruning, and deletion all mutate existing neighbour lists. A fixed-capacity array
gives O(1) insertion into a free slot, O(M0) swap-erase, one allocation, predictable
stride, and no offset table to maintain. The waste is bounded by the degree cap.

**Consequences.** `M0 = 2 * M` by default (e.g. 32 for M=16). Validation checks
`degree <= M0` at layer 0 and `degree <= M` above. This is the representation the
interview answer should defend.

## D5 — The store owns the vectors; the indexes borrow them

**Decision.** `VectorStore` owns one flat `std::vector<float>` (plus dimension and
size). `BruteForce` is a lightweight view over a store. `HNSW` holds a
`const VectorStore&` and owns only graph slots. No index copies the vectors.

**Why.** At 1M a duplicate store costs another 512 MB and makes the BF cross-check
ambiguous: two copies can drift. The store is the single source of truth; BF and
HNSW must see the same slots.

**Consequences.** The public `SearchableIndex` interface is minimal:
`search(span, k, ef)`, `size()`, `dim()`. Mutation is not in the base interface.
`HNSW` has `build()` and `insert(slot)` for construction/tests. Brute force does not
pretend to be a mutable index.

## D6 — v1 is single-threaded

**Decision.** One thread, one query at a time, no `shared_mutex`, no TSan, no
four-thread contention benchmark in v1.

**Why.** Concurrency is 2–4 sessions of hard debugging and does not improve the
recall claim. The benchmark's headline is a single-thread number, which is easier to
compare with literature. A correct single-threaded index is a stronger interview
artifact than a half-finished thread-safe one.

**Consequences.** The README states "1 thread". The `hns_core` API does not promise
thread safety. A thread-safe wrapper is a stretch item, added only if a real
consumer exists.

## D7 — No physical deletion in v1

**Decision.** v1 has no `remove()` in the public API. If deletion is added later, it
is mark-deleted: deleted nodes remain as routing nodes, are filtered from results,
and are counted separately from live nodes. Physical edge erasure is a stretch item.

**Why.** Delete is the hardest part of HNSW and is not needed for the headline
claim. The plan's own research notes that hnswlib keeps deleted nodes as routers;
naive physical deletion can disconnect the graph. A 20%-delete test is too weak to
prove safety.

**Consequences.** `size()` is the number of live vectors. A future `slot_count()`
includes tombstones. Tests cover deleted IDs never returned, live neighbours still
found, entry/top-layer behaviour, and reinsertion.

---

## D8 — v1 has no persistence, server, WASM, cosine set, pgvector, or KDTree

**Decision.** All of these are stretch items, documented in `plan.md` §12. They are
not in the 28-session v1 schedule.

**Why.** Each is a multi-session detour and a new bug surface. The claim is a
single-threaded, in-memory, L2, SIFT-100k measurement with a static showcase. A
server reintroduces HTTP, CORS, deploy, and a second set of numbers on different
hardware. WASM requires a second toolchain. Cosine requires a second dataset and a
second ground truth. KDTree dies in 128 dimensions and is decoration.

**Consequences.** Any future addition gets its own decision entry and its own
measurement. It never silently changes the v1 claim.

## D9 — The trace hook is compile-time; the exporter lives outside the core

**Decision.** `hns_core` exposes `template <bool Trace> searchImpl(...)` with a
`TraceSink*`. The public `search()` instantiates `Trace=false`; `searchTraced()`
instantiates `Trace=true`. JSON/CSV writing lives in `hns_io`; `hns_bench` calls it
after timed trials. The core has no `main`, no paths, no `ifstream`, no JSON.

**Why.** A virtual `onVisit()` in the hot loop is not free, and a core that writes
files cannot compile to WASM or be tested without a filesystem. The traced and
untraced paths must produce identical IDs and distances; that is a test.

**Consequences.** The timed benchmark never pays for instrumentation. The exporter
records events/deltas (layer enter, visit, candidate push/pop, result update), not
the full beam at every step. Query subgraphs are capped at ~500 nodes.

## D10 — Build once per configuration; five query trials

**Decision.** A benchmark configuration is `(dataset, M, efConstruction)`. Build the
index once, measure build time once, warm up 100 queries, then run 5 timed passes
over the query set. `efSearch` sweeps reuse the same build. The BF baseline is
computed once per `(dataset, query set, k)` and cached. No persistence in v1.

**Why.** "5 fresh processes per config" with no save/load means rebuilding the graph
five times and conflates build variance with query variance. It makes 1M sweeps
impossible and wastes the schedule. Build once, query many is the only practical
protocol here.

**Consequences.** Per-trial QPS/p50/p95/p99 are reported, plus the median and
min/max across trials. A fresh process is used per configuration, not per trial. If
process isolation per trial is ever required, it waits for a serialized index.

## D11 — The showcase is three static pages, not a dashboard

**Decision.** v1 pages: `/` (claim, curve, table, method, reproduce), `/trace`
(query-centric graph **and** replay in one page), `/prune` (two-cluster proof).
About/fine print is a footer. No separate `/graph`, `/about`, or `/playground` in v1.
WASM playground is a stretch item.

**Why.** `/graph` and `/trace` show the same insight and compete for attention. The
trace page is the differentiator. The site is a visual aid, not the project. Three
pages fit four sessions; five pages do not.

**Consequences.** The JSON contract has one `queries/q0042.json` containing graph,
trace, and result. Graph size is capped at 500 nodes. The site never computes a
headline number; it only renders artifacts with a `run_id`.

## D12 — 28 sessions, ~70 hours, 10–12 weeks at 7–8 h/week

**Decision.** The canonical plan is 28 sessions of 2–3 hours: S1–S22 core, S23–S26
showcase, S27–S28 ship/buffer. At 7 h/week this is ~10 weeks plus slippage; at
8 h/week ~9 weeks plus slippage; at 10 h/week ~7 weeks plus slippage.

**Why.** The old docs mixed 24 × 4 h, 32 × 2–3 h, and an 8–10 week / 1 h-per-day
schedule. The arithmetic did not close: 32 × 2.5 h = 80 h, which is 11.4 weeks at
7 h/week before slippage. HNSW debugging also needs continuity; 1 h/day is worse
than three 2–3 h blocks per week.

**Consequences.** If only 1 h/day is available, expect 11–12 weeks, not 8–10. If the
deadline is fixed at 8 weeks, cut the showcase and the 1M run, not the data/GT gate.

## D13 — Release build from Session 1; flags are recorded

**Decision.** The benchmark build is CMake `Release` with `-O3 -DNDEBUG` (plus
`-march=native` for the headline run, recorded in the manifest). Tests use a separate
sanitizer build. CI uses `-O3 -DNDEBUG` without `-march=native`. Print the build type
and flags at startup. Do not enable `-Werror -Wconversion -Wsign-conversion` in the
first weeks; use `-Wall -Wextra`, tighten later.

**Why.** A default CMake build can be `-O0`; a beginner can "pass" a p50 checkpoint
with numbers 10–50× too slow. Flags are part of the measurement. `-Wconversion`
noise around `size_t`/`Slot` is not a good first-week debugging task.

**Consequences.** Every CSV/JSON row carries compiler, version, flags, and build type.
The headline run is reproducible only on the named machine; CI numbers are not
headline numbers.

---

## D14 — No number ships without an artifact and a commit

**Decision.** The README, showcase, resume bullet, and demo use only values from a
frozen run: `dirty=false`, `run_id`, `commit`, dataset/query/GT checksums, machine,
flags. Illustrative examples in docs are marked `illustrative` or replaced with
`X/Y/Z`. No hardcoded "500×", no interpolated points, no "about" numbers.

**Why.** The project's only asset is trust. One invented number invalidates the
rest. A measured 100k row is more impressive than a borrowed 1M story.

**Consequences.** The exporter refuses to publish a dirty tree. The site's schema
checker rejects incomplete rows. The README table stays `TBD` until S22.
