## D1 — v1 is one product with one measured engine

**Decision.** v1 is a single project with two layers:

- **Product:** the HNSWhy React UI — upload PDF, Markdown, or plain text (or
  paste text), ask questions, read answers with citations, inspect a 2D and 3D
  embedding map, and open a benchmark tab.
- **Engine:** a from-scratch C++20 HNSW library — flat vector store, exact brute force,
  HNSW insert/search/prune, mark-deleted, tests, and a SIFT benchmark.

The public claim is: **a RAG app a stranger can use, backed by an index written from
scratch, with a benchmark a stranger can reproduce.**

**Why.** A RAG wrapper alone is common and easy to dismiss. A benchmark-only repo is
invisible to most recruiters and unusable as a demo. The merge gives the project a
visible product surface and a defensible engineering core. The engine is what makes
the product more than a prompt around a vector library; the product is what makes the
engine worth looking at.

**Consequences.**

- HTTP API, SQLite persistence, document deletion, configurable local/remote
  providers, and a React frontend are in v1.
- The engine remains a static C++ library. It is not a microservice, a distributed
  system, or a separate deployed service.
- The frontend is built from scratch in this repo (`frontend/`) with React 19,
  TypeScript, and Vite; it is not imported from an earlier prototype. It
  implements the four tabs and the `/api/*` contract in this file. See D24.
- The old three-page static showcase is retired. The product UI is the showcase.

## D2 — SIFT-100k is the graded benchmark; 1M is optional later

**Decision.** The headline benchmark is the first 100,000 vectors of SIFT-1M, all
10,000 queries, with ground truth generated by our own brute force over that exact
prefix. SIFT-1M is an optional single-configuration scale run **after** v1 ships.

**Why.** 100k is 51.2 MB of vectors, builds in minutes, and can be iterated on in one
sitting. 1M is 512 MB and makes every sweep and every brute-force ground-truth pass
10× more expensive. The claim is about the algorithm and the measurement, not the
largest possible N. A valid 100k answer key is worth more than an invalid 1M one.

**Consequences.** Every chart, README line, resume bullet, and benchmark-tab label
says `N = 100,000` unless a measured 1M row exists. 1M is never a sweep. The engine
supports 1M; v1 does not depend on it.

**Revisit.** After v1 ships, if the 100k run is stable and the 1M build fits the time
budget, run one 1M configuration and add a separate, clearly labelled row.

## D3 — Ground truth is generated for the exact dataset, never borrowed

**Decision.**

| Dataset | Base | Queries | Ground truth | Use |
|---|---:|---:|---|---|
| `siftsmall` | 10,000 | 100 | shipped `siftsmall_groundtruth.ivecs` | loader proof only |
| `sift10k` | first 10,000 of 1M | 1,000 | **our BF top-100, IDs + distances** | CI and integration |
| `sift100k` | first 100,000 of 1M | 10,000 | **our BF top-100, IDs + distances** | graded v1 |
| `sift1m` | 1,000,000 | 10,000 | shipped `sift_groundtruth.ivecs` + BF sample | optional scale run |

The shipped SIFT answer key is defined over **all 1,000,000 vectors**. It is invalid
on any subset. Never score a 100k or 10k index against it.

For `sift10k` and `sift100k`, generate the top-100 by brute force over that exact
base and query set. Store IDs **and** distances, checksum the file, and record the
generator commit and flags. Commit a self-contained CI bundle under
`tests/fixtures/sift10k/`: the first 10k base, a fixed 1k query set, ground-truth IDs
and distances, query IDs, and SHA-256. The 100k ground truth is generated by
`scripts/run_bench.sh` into gitignored `data/sift100k/` and recorded by hash in the
release report; the 100k base is not committed.

**Tie rule.** Recall is distance-threshold based: a returned item counts if its
distance is ≤ the true k-th distance + `1e-6`. Report ID-overlap recall separately.
SIFT squared-L2 is integer-valued, so exact ties happen.

**Why.** The most expensive mistake in this kind of project is a broken ruler. If the
answer key is wrong, every later number is wrong and the graph gets tuned against
noise. The prefix rule is not a detail; it is the difference between a valid result
and a meaningless one.

**Consequences.** The brute-force generator is the same BF code that is under test,
so validate a 100-query sample against an independent float64 reference. `siftsmall`
against its shipped key is the independent loader check; `sift10k`/`sift100k` against
our own key is a consistency check, not independent correctness evidence.

## D4 — 10,000 queries for the headline; 1,000 for smoke; three trials

**Decision.** The headline uses all 10,000 SIFT queries. A fixed 1,000-query subset
is allowed for per-PR smoke tests and regression comparisons; it is labelled
`PRELIMINARY` and never published as the headline. The benchmark builds the index
once, warms up, and runs **three** timed passes over the query set. Report the mean
and the min/max across passes. A 95% bootstrap interval is optional in `bench.json`;
it is not a release gate.

**Why.** Ten thousand queries is enough to report a stable mean without turning the
benchmark into a statistics project. Three passes catch obvious noise without
pretending a laptop is a controlled experiment. A CI interval is useful context, but
a gate that flips on sampling noise is worse than no gate. The CI smoke test uses a
fixed 1,000-query set and a frozen recall floor, not a confidence-interval gate.

**Consequences.**

- CI runs `sift10k` with 1,000 queries and requires `R@10 ≥ 0.90` at the chosen
  config. QPS is reported but never gated on shared runners.
- The 100k headline reports mean `R@10`, mean QPS, p50/p95/p99, build time, RSS, and
  distance computations. It does not claim a confidence interval it did not compute.
- The release report includes a small `efSearch` curve from the same build; each point
  uses the same three-pass protocol. The headline is the pre-registered SLO point, not
  the best point on the curve.
- A 1k smoke number is always labelled `PRELIMINARY`.
- If the three passes disagree wildly, investigate the machine before publishing.

## D5 — Layer 0 uses fixed-capacity flat adjacency, not CSR

**Decision.** Layer 0 stores `M0` neighbour slots per node in one flat
`std::vector<uint32_t>` (`N * M0`) plus a `std::vector<uint16_t>` degree array.
Pruning swap-erases within the node's fixed slots. Upper layers are sparse and may
use per-node small vectors or per-layer slabs. The `vector<vector<...>>` ban applies
to layer 0 and to per-vector float storage, not to the thin upper layers.

**Why.** CSR is a static layout. HNSW is built incrementally: insert, back-edge
pruning, and deletion all mutate existing neighbour lists. A fixed-capacity array
gives O(1) insertion into a free slot, O(M0) swap-erase, one allocation, predictable
stride, and no offset table to maintain. The waste is bounded by the degree cap.

**Consequences.** `M0 = 2 * M` by default (e.g. 32 for `M = 16`). Validation checks
`degree <= M0` at layer 0 and `degree <= M` above. This is the representation the
interview answer should defend.

## D6 — The store owns the vectors; the indexes borrow them

**Decision.** `VectorStore` owns one flat `std::vector<float>` plus dimension and
size. `BruteForce` is a lightweight view over a store. `HNSW` holds a
`const VectorStore&` and owns only graph slots. No index copies the vectors.

**Why.** At 1M a duplicate store costs another 512 MB and makes the BF cross-check
ambiguous: two copies can drift. The store is the single source of truth; BF and
HNSW must see the same slots.

**Consequences.** The public `SearchableIndex` interface is minimal: `search(span, k,
ef)`, `size()`, `dim()`. Mutation is not in the base interface. `HNSW` has `build()`
and `insert(slot)` for construction and tests. Brute force does not pretend to be a
mutable index.

## D7 — The engine is single-threaded; the API serializes access

**Decision.** One engine thread, one query at a time. No `shared_mutex`, no TSan, no
four-thread contention benchmark in v1. The HTTP server may accept concurrent
requests, but every call that touches the engine or the document index goes through
one API-level mutex.

**Why.** Concurrency is days of hard debugging and does not improve the recall claim.
The benchmark's headline is a single-thread number, which is easier to compare with
literature. A correct single-threaded index is a stronger interview artifact than a
half-finished thread-safe one. Serializing at the API layer is the honest tradeoff
for a local demo.

**Consequences.** The README states "1 engine thread; API serializes engine access."
The engine API does not promise thread safety. A concurrent read path is a stretch
item, added only if a real consumer exists. The API must not silently interleave an
insert with a search.

## D8 — Deletion is mark-deleted, not physical

**Decision.** v1 includes `HNSW::remove(slot)`, implemented as mark-deleted. The node
stays in the graph as a routing node, is filtered from results, and is counted
separately from live nodes. The SQLite document row is deleted in the same operation
(cascade removes its chunks and embeddings). On restart the index is rebuilt from the
remaining rows, so tombstones disappear. Physical edge erasure and graph compaction are
deferred.

**Why.** The product needs document deletion. Physical deletion is the hardest part
of HNSW and can disconnect the graph; a deleted entry point or a removed bridge can
silently destroy recall. Mark-deleted is the standard safe answer: keep the route,
hide the result. The old "no delete in v1" decision was correct for a benchmark-only
project and wrong for a product.

**Consequences.**

- `size()` is the number of live vectors. `slot_count()` includes tombstones.
- Query search traverses deleted nodes but never returns them.
- Insertion treats tombstones as ordinary candidates, so a new node can attach after a
  delete-all; queries still exclude them.
- The entry point may be deleted; it still routes.
- Reinsertion uses a new slot; slots are not reused.
- Tests cover deleted IDs never returned, live neighbours still found, entry/top-layer
  behaviour, and restart after deletion.
- SQLite is the source of truth; a restart rebuilds without tombstones.

## D9 — SQLite is the source of truth; HNSW is rebuilt on startup

**Decision.** Documents, chunks, and embeddings live in SQLite. The HNSW graph is an
in-memory derived index. On startup the server loads chunks and embeddings, builds the
graph, and serves. There is no graph snapshot in v1.

**Why.** Persistence is required by the product: a user expects uploaded documents to
survive a restart. Serializing a mutable HNSW graph is a second format with its own
corruption, versioning, and consistency bugs. Rebuilding from the source data is
simpler, cannot drift from SQLite, and is fast enough at the target size. The graph is
an index, not the database.

**Consequences.**

- Schema: `documents`, `chunks`, `embeddings`; `embeddings.chunk_id` references
  `chunks.id`. Engine slots are runtime-only and live in `slot_to_chunk_`.
- Vectors are stored as float32 BLOBs with a dimension check.
- On insert: commit document/chunks/embeddings, then add each vector to the store and
  insert the returned slot into the live graph. If the process dies between those
  steps, startup rebuild repairs the graph.
- On delete: delete the document row (cascade removes chunks and embeddings) and call
  `HNSW::remove(slot)` using the in-memory slot mapping.
- Startup rebuild is measured and reported for the product dataset, not folded into
  the SIFT benchmark.
- A graph snapshot is a stretch item with its own corruption test.

## D10 — The graph is directed, not symmetric

**Decision.** Adjacency is directed. When a new node is connected, edges are added in
both directions as a starting point; pruning is one-sided and may remove one
direction without removing the other. There is no symmetry invariant.

**Why.** Standard HNSW implementations use directed adjacency. Enforcing symmetry is
an extra constraint on every prune, can remove useful one-way links, and adds a
reciprocal-cleanup path that is easy to get wrong. The property that matters is
search quality and reachability, not a pretty symmetric matrix.

**Consequences.**

- Validation checks no self-loops, no duplicate edges, degree caps, layer membership,
  entry/top-layer consistency, and `levelCount` consistency. It does **not** check
  symmetry.
- Tests measure reachability from the entry point and recall on `sift10k`; a directed
  graph can have unreachable nodes, and that is a quality bug, not an invariant
  violation.
- The old spec's "if u lists v, v lists u" rule is removed.
- Back-edge pruning uses the neighbour as the reference, not the newly inserted node.

## D11 — The benchmark is a CLI, not a live API

**Decision.** `hns_bench` reads SIFT, builds the index, times queries, and writes
`bench.json`. The web API exposes the latest report from that file; it never runs the
100k benchmark inside an HTTP request.

**Why.** A live benchmark in the API would mix network latency, JSON serialization,
Ollama, and whatever else the server is doing into the number. A CLI run is
controlled, repeatable, and can be executed on a named machine. The product and the
evidence stay separate.

**Consequences.**

- `GET /api/benchmark` returns the report or a clear "no report" state.
- The release report is committed as `docs/results/bench.json`; the raw dataset stays
  in gitignored `data/`. Local scratch runs may write `data/bench.json`.
- The Benchmark tab reads that endpoint; it does not ship a second benchmark
  implementation.
- The benchmark command and its parameters are shown in the UI and README.
- Product latency (`/api/ask`) is reported separately and is never presented as the
  SIFT benchmark.

## D12 — The product UI is the showcase; there is no separate static site

**Decision.** v1 has four product tabs: **Documents**, **Ask**, **Map**, and
**Benchmark**. The old static `/`, `/trace`, and `/prune` site is retired. The
product itself is the demo.

**Why.** A separate static site duplicates the story, adds a second build and deploy,
and is less convincing than a working product. The benchmark tab can show the curve,
the table, and the prune explanation without a second frontend. The product gives a
stranger something to do; the benchmark tab gives them something to check.

**Consequences.**

- No `web/` static site in v1.
- No trace-replay page or visited-node overlay. The Map shows real embeddings and
  retrieved hits; replay is not v1.
- The Map ships in 2D and 3D. The 3D view was added after the 2D view and retrieval
  were measured; it is still a projection of real embeddings, not a graph drawing.
- The prune explanation lives in the Benchmark tab or README, not a separate route.
- The demo is the product flow, not a slideshow.

## D13 — One distance metric: squared L2; normalize product embeddings

**Decision.** The engine and the SIFT benchmark use squared L2. For product
embeddings, normalize every document and query vector before insertion/search. On
unit-length vectors, L2 ranking is equivalent to cosine ranking.

**Why.** SIFT is an L2 dataset; adding a cosine dataset and a second ground truth
doubles the measurement work for no product benefit. Ollama embedding models are
typically compared with cosine. Normalizing once at the boundary gives the product
the ranking it expects while keeping one engine code path.

**Consequences.**

- No cosine-specific index, no multi-metric benchmark, no metric flag in v1.
- The normalization is tested: `||v|| ≈ 1`, and a known pair ranks the same under
  cosine and squared L2 after normalization.
- If a future embedding model requires a non-L2 metric, it gets its own decision and
  its own ground truth.

## D14 — 2D and 3D map; no KD-tree

**Decision.** The Map tab projects real embeddings to two or three dimensions with
PCA. It samples at most 2,000 points for display and highlights the query and
retrieved chunks. The 3D view is an additional projection of the same data, not a
different index or a drawing of HNSW edges. There is no KD-tree.

**Why.** A 3D view helps show cluster separation and retrieval neighbourhoods that a
2D projection flattens. It was added only after the 2D map, retrieval, and benchmark
were working, so it did not delay the core proof. A KD-tree is a valid exact index in
low dimensions and a poor one at 128 or 768 dimensions; adding it would be decoration,
not depth.

**Consequences.**

- `frontend/src/lib/pca.ts` implements a small NIPALS PCA over the sampled embedding
  matrix; no external charting or projection service.
- The 2D view is SVG; the 3D view is a canvas projection with orbit, pan, and zoom.
- The map is labelled with the source dimension, the projection dimension, and the
  number of sampled chunks. Distances in the projection are approximate.
- No KD-tree source file, no KD-tree benchmark row, no 3D library dependency.

## D15 — Release build from the start; flags are recorded

**Decision.** The benchmark build is CMake `Release` with `-O3 -DNDEBUG` (plus
`-march=native` for the headline run, recorded in `bench.json`). Tests use a separate
sanitizer build. CI uses `-O3 -DNDEBUG` without `-march=native`. Print the build type
and flags at startup. Do not enable `-Werror -Wconversion -Wsign-conversion` early;
use `-Wall -Wextra`, tighten later.

**Why.** A default CMake build can be `-O0`; a beginner can "pass" a p50 target with
numbers 10–50× too slow. Flags are part of the measurement. `-Wconversion` noise
around `size_t`/`Slot` is not a good early debugging task.

**Consequences.** Every `bench.json` row carries compiler, version, flags, and build
type. The headline run is reproducible only on the named machine; CI numbers are not
headline numbers.

## D16 — No number ships without an artifact

**Decision.** The README, benchmark tab, resume bullet, and demo use only values from
a frozen run: `run_id`, commit, dataset/query/GT SHA-256, machine, compiler, flags,
thread count, and build type. Illustrative examples in docs are marked `illustrative`
or replaced with `X/Y/Z`. No hardcoded "500×", no interpolated points, no "about"
numbers.

**Why.** The project's only asset is trust. One invented number invalidates the rest.
A measured 100k row is more impressive than a borrowed 1M story.

**Consequences.**

- `hns_bench` writes `bench.json`; the README table and Benchmark tab read it.
- The README table stays `TBD` until the v1 release run.
- The UI shows the command and the run metadata, not just a pretty curve.
- If a number is not in `bench.json`, it does not go on a slide.

## D17 — Work is self-paced; the scope is fixed, not the calendar

**Decision.** No fixed work-block count, hour target, or calendar deadline is part of
the plan. Work proceeds in self-directed sprints. The scope in D1 and D20 is the
commitment; the order is dependency-driven: trusted data, then the engine, then the
product flow, then the benchmark, then the deploy and demo.

**Why.** A fixed calendar was overhead the project did not need. The deliverable is a
working product and a measured engine, not adherence to a calendar. HNSW debugging
needs continuity, which a self-paced sprint gives you.

**Consequences.** There is no calendar to fall behind. Progress is judged by
artifacts and gates, not by work blocks completed. If a deadline appears, cut the
stretch list, not the data/GT gate or the product's core flow.

## D18 — The claim is product + measured engine; the heuristic ablation is secondary

**Decision.** The public claim is not "I implemented HNSW." It is: **a RAG app a
stranger can use, backed by a from-scratch C++ HNSW engine, measured against exact
search on SIFT-100k, with tests and a reproducible benchmark.** The diversity-heuristic
ablation — nearest-only vs heuristic at the headline configuration — is a supporting
experiment, not the whole project.

**Why.** The old benchmark-only framing was too narrow to be visible and too easy to
read as "another HNSW implementation." The product makes the work legible; the
benchmark makes it credible. The ablation is a good differentiator, but it only
matters after the product and the main measurement exist.

**Consequences.**

- README first line and demo opener lead with the product and the measured engine.
- The benchmark tab shows the main curve first; the ablation is a later experiment,
  not a v1 panel.
- Optional after v1: one extra nearest-only build at `M=16`, `efC=200`, with the same
  query grid as the headline (the chosen SLO point; `ef=50` only if that is the SLO
  point). No code fork; a runtime flag selects the prune strategy. If it is not run, do
  not show an ablation panel; the two-cluster test is the v1 evidence for the heuristic.
- If the ablation says the heuristic barely helps at 100k, publish that. A measured
  null result is still a result.
- No claim of novelty. HNSW is a published algorithm.

## D19 — One active project until v1 ships

**Decision.** No second project, no rebuild, no "better idea" until the v1 claim
exists. RepoGraph (0 LOC) and PushInbox (0 LOC, a duplicate of the already-shipped
ReachInbox) are parked. The portfolio is **HNSWhy (deep) + ReachInbox
(medium, hardened)**, not three deep projects.

**Why.** A second deep project does not fit before the placement season. The failure
mode is recorded: three days of project selection produced zero lines of code.
Switching projects is the most expensive form of procrastination available, and it
feels like work.

**Consequences.**

- A new project idea goes into the parked list below, not into a new repo or a new
  planning document.
- The docs are revised in place after this date, not forked into a new plan.
- Revisit after v1 ships, not before. The only exception is a paid or deadline-bound
  opportunity.

**Parked list (do not start):**

| Idea | Status | Revisit |
|---|---|---|
| RepoGraph | docs only, 0 code | after v1, if ever |
| PushInbox | duplicate of ReachInbox; large scope | never as a separate project; harden ReachInbox instead |
| Financial ledger | highest-scoring alternative from the old blueprint comparison | after the first job, if the target is generic backend |
| A second vector project | would duplicate this one | no |

## D20 — The cut list is part of the scope

**Decision.** The following are deliberately not in v1:

- 1M sweep (one optional run after v1)
- KD-tree
- multi-metric benchmark
- cosine-specific index
- physical graph deletion / compaction (SQLite rows are deleted; the in-memory node
  is mark-deleted)
- graph snapshot / load
- concurrent engine access
- auth, multi-user, tenancy
- agents, Graph RAG, tool calling
- distributed or multi-node search
- static showcase site
- trace-replay page
- live benchmark endpoint

The 3D map and PDF extraction were moved off this list when they shipped in v1:
the 3D map arrived after the 2D map and retrieval were measured (D14), and PDF
extraction uses the existing `pdftotext` dependency with a tested failure path (D23).
Everything else above remains deliberately out of scope.

**Why.** Every item above is a real feature with a real bug surface. None is needed
to prove the v1 claim: a usable RAG product and a measured 100k HNSW engine. The
fastest way to finish is to keep the cut list closed.

**Consequences.** An item returns only with a new decision entry, a reason tied to a
user or a measurement, and a place in the definition of done. "It would be cool" is
not a reason. The cut list is reviewed after v1, not during it.

## D21 — The default providers are offline and deterministic

**Decision.** The default embedding provider is `local-hash-v1`, a deterministic
hashed bag-of-words embedder with 256 dimensions. The default chat provider is
`local-extractive-v1`, an extractive answerer. Both are selected only when no external
provider is configured. Ollama and OpenAI-compatible endpoints remain fully
configurable.

**Why.** A fresh clone must run without Ollama, an API key, or network access. A demo
that only works after a model download is a worse artifact than one that always works
offline and can be upgraded later. The hash embedder is a real, reproducible embedding
function; it is not a placeholder that fabricates vectors at render time.

**Consequences.** The sample knowledge base seeds with the hash provider. Switching to
another embedding space requires `--reembed`. Search quality with the hash provider is
honest but limited; the README says so.

---

## D22 — Provider, model, and dimension are persisted; never mix spaces

**Decision.** SQLite metadata records the active embedding provider, model, and
dimension. On startup, a mismatch with the configured provider refuses to open the
library unless `--reembed` is passed. `--reembed` recomputes every chunk vector and
rebuilds the index.

**Why.** Vectors from different models are not comparable. Silently mixing them
produces plausible-looking but meaningless retrieval. An explicit, maintenance-heavy
operation is better than a silent correctness bug.

**Consequences.** The error message names the stored and configured spaces and the
remediation command. Tests cover the mismatch refusal and the successful re-embed.

---

## D23 — PDF extraction uses `pdftotext`

**Decision.** PDF uploads shell out to `pdftotext` (Poppler) and fail with a clear API
error when the binary is missing or extraction yields no text. No PDF parser is
vendored.

**Why.** PDF parsing is a large dependency and a bug surface unrelated to the engine.
`pdftotext` is available on the target machine and does the job. The product still
accepts PDF, TXT, and Markdown as promised.

**Consequences.** Setup documents the Poppler prerequisite. Tests cover the failure
path without requiring a PDF fixture at build time. Markdown and plain text need no
external binary.

---

## D24 — The frontend is built from scratch

**Decision.** The React 19 + TypeScript + Vite frontend in `frontend/` is written for
this repository. It is not an earlier prototype UI imported wholesale.

**Why.** The old UI was built around different routes and a fake 16D embedding path.
Adapting it would have carried dead assumptions into the product. A clean build made
the four tabs, the `/api/*` contract, and the visual system match the shipped backend.

**Consequences.** The UI has its own components, theme tokens, icons, map renderers,
and tests. No old bundle or route is served.

---

## D25 — Tombstones stay traversable

**Decision.** Deleted vectors are marked in the graph. Queries traverse tombstones but
filter them from results. Insertion beams include tombstones, so a new node can attach
after every previous node was deleted. Physical compaction is deferred.

**Why.** Removing a node from a proximity graph can disconnect live nodes and destroy
the entry point. Traversal is the thing that must survive deletion. Filtering at the
result boundary preserves reachability without lying about live results.

**Consequences.** The index reports tombstones separately from live vectors. Restart
rebuilds from SQLite and resets the count. Tests cover deleting the entry point,
deleting everything and reinserting, and queries after deletion.

---

## D26 — The diversity prune keeps exact duplicates

**Decision.** The diversity heuristic keeps exact duplicates (`d(c, s) == 0`) up to
the degree cap instead of rejecting them as redundant.

**Why.** Rejecting duplicates turned copies into one-way leaves, so a query could not
reach every duplicate and returned fewer than `k` results. Keeping them is the
behaviour that matches the graph contract.

**Consequences.** Duplicate-heavy inserts retain recall and result count. The prune
tests include an all-identical set.

---

## D27 — Ground truth is recomputed for the exact benchmark prefix

**Decision.** The SIFT-100k ground truth is generated with our own exact `BruteForce`
over the exact 100k prefix and all 10,000 queries. The shipped SIFT-1M answer key is
not used. The benchmark verifies the exact baseline against that key before reporting
HNSW numbers.

**Why.** The shipped key is defined over 1,000,000 vectors; scoring a 100k prefix
against it is meaningless. The generator is the same BF code under test, so the
benchmark also checks a 100-query float64 reference and the siftsmall shipped key for
independent evidence.

**Consequences.** The report records the ground-truth file paths, config, compiler,
hardware, dataset counts, and the exact-baseline check. A baseline mismatch aborts the
run instead of publishing numbers.

---

## D28 — The Map projects embeddings, not the HNSW graph

**Decision.** The Map tab samples chunk vectors, projects them with a client-side
NIPALS PCA, and renders 2D (SVG) and 3D (canvas) views. It is an embedding-space
visualization with retrieval highlights and point inspection. It does not draw HNSW
edges or replay a search.

**Why.** A real projection shows cluster structure and outliers that explain retrieval
behaviour. A fake graph drawing would look technical while proving nothing.

**Consequences.** The UI labels the source dimension, projection dimension, and sample
count. The server caps the sample; the client never invents points. A query overlay
appears only after a real `/api/ask` response.

---

## D29 — The sample knowledge base seeds only a fresh database

**Decision.** Eight Markdown documents (16 chunks) ship under `samples/`. They are
embedded with the configured provider and inserted only when the database has no
documents. `--no-sample` starts empty. Existing user data is never overwritten.

**Why.** An empty product is a bad first demo. Overwriting a user's library is worse.
A fresh-database guard gives the demo content without risking data loss.

**Consequences.** The sample is documented in the README. Tests cover the seed guard.
Deleting a sample document is permanent for that database.

---

## D30 — One server process owns the database

**Decision.** `DocumentStore` takes an exclusive non-blocking `flock` on `<db>.lock`
for the process lifetime. A second process that opens the same database fails at
startup with a clear message. The descriptor is opened `O_CLOEXEC` and the lock file
is `0600`.

**Why.** SQLite tolerates concurrent writers, but the in-memory HNSW graph does not:
each process would index only the rows it knew about and return stale neighbours. The
graph is an acceleration structure, not a cache that can be shared through SQLite.

**Consequences.** Tests that reopen the same database must close the first
`Application`; `test_persistence` does. Read-only inspection of a live database uses
`sqlite3` directly, which is unaffected by the advisory lock.

---

## D31 — A disconnected graph falls back to exact search

**Decision.** `HNSW` caches whether layer 0 reaches every live node. After any insert
or removed edge the cache is invalidated. If a search finds the graph disconnected, it
scans the live vectors exactly and reports `SearchStats::exact_fallbacks`.

**Why.** Tombstones and pruning can strand a component without breaking the graph's
structural invariants. Returning a silently truncated neighbour list would make recall
look fine on average and fail on the one query that matters.

**Consequences.** Recall cannot collapse on a damaged graph; worst-case latency for
that query is an exact scan. Tests assert the counter, and the regression test on seed
6942 reproduces the old stale-cache failure.

---

## D32 — Inputs are validated at the boundary

**Decision.** The API returns 415 when `/api/ask` or a JSON upload carries a
non-JSON `Content-Type`. Benchmark numeric flags accept decimal digits only and reject
`--ef 0`. The ground-truth cache is stamped with SHA-256 hashes of the base, query,
prefix, and `k`, so a changed input invalidates it.

**Why.** Parsing an arbitrary body as JSON produces confusing 400s, and a stale
ground-truth file would make the benchmark compare against the wrong answer key while
still printing a plausible recall number.

**Consequences.** Clients must send `Content-Type: application/json` for JSON bodies;
multipart uploads are unaffected. Changing the dataset or `k` costs one ground-truth
recomputation, which is the correct trade.
